## 1. Bugs Found

1. **P0-A** — `Iteration 1` stored hard-coded `candidateCount` (5 = `candidateCountPerIteration`) instead of the actual 20 candidates generated by the initial SearchRun. `/api/loop/start` was passing `parsed.data.candidateCountPerIteration ?? 5` to `registerInitialSearchRun` instead of querying the DB for the real count.
2. **P0-B** — `SearchCompleted` event was incorrectly treated as iteration completion. It actually fires after candidate generation, not after evaluation. The runner subscribed to `SearchCompleted` and bumped `currentIteration` immediately, leaving Iteration 1 in `RUNNING` with all evaluations still pending.
3. **P0-C** — Race: `SearchCompleted` fired before `registerInitialSearchRun`. The runner listened for `SearchCompleted` to advance iterations; if the event fired before the loop was registered, the runner had no idea what to do and the iteration stalled.
4. **P1-A** — `read-modify-write` counter updates on `LoopRunState.totalEvaluated` and `noImprovementCount` raced under concurrent `StrategyEvaluated` events.
5. **P1-B** — `noImprovementCount` was being incremented by both the orchestrator AND the runner, double-counting and breaking stop semantics.
6. **bestStrategyVersionId stayed null on LoopRunState** — orchestrator's CAS-update of `bestScoreSoFar` ran but the runner's `improved` check used `>` only and would never copy the identity fields if the score matched.
7. **Duplicate `StrategyEvaluated` events** for the same `candidateId` inflated `totalEvaluated`. PowerShell script's HTTP timeout caused the script to retry, generating new experiments for the same candidate.
8. **Failed backtests stalled iterations** — parameter validation errors in the HybridLoopGenerator mutations produced FAILED experiments without emitting `StrategyEvaluated`, so iterations containing failed candidates never reached `evaluatedCount == candidateCount`.
9. **`/api/loop/candidates` omitted `searchRunId`** per iteration, blocking the e2e script from retrieving Iteration 2's SearchRun id for manual backtests.
10. **Frontend `Loop.tsx` displayed wrong metric** — used `candidateCountPerIteration` (5) for "Current Iteration" denominator, which was wrong for Iteration 1 where the real count was 20.

## 2. Root Causes

| Bug | Root Cause |
|-----|------------|
| P0-A | Hard-coded fallback in `/api/loop/start` |
| P0-B | Confused event semantics: `SearchCompleted` ≠ `IterationCompleted` |
| P0-C | Event-driven iteration lifecycle with no DB-state check on registration |
| P1-A | Non-atomic counter mutations under concurrent events |
| P1-B | Two writers updating the same field with no ownership contract |
| Best strategy null | Orchestrator writes `bestScoreSoFar` only; runner writes identity only on strict `>` |
| Duplicate inflation | No idempotency on event-candidate pairs |
| Stalled iterations | Missing "count failed candidates" path |
| Missing `searchRunId` | Iterations API serialization omitted the column |
| Frontend wrong count | Used global config field instead of per-iteration DB field |

## 4. Architecture Changes

```
Iteration N (RUNNING)
  │
  ▼
Candidate StrategyGenerated event (auto-enqueued → backtest → evaluation)
  │
  ▼
StrategyEvaluated event (per candidate, idempotent per candidateId)
  │
  ▼
LoopOrchestratorService.handleStrategyEvaluatedForLoop(payload)
  │  • dedupe check (Set<candidateId>)
  │  • Branch A (improved): CAS-update bestScoreSoFar + reset noImprovementCount
  │  • Branch B (no-improvement): increment totalEvaluated + noImprovementCount
  │  • per-iteration CAS update of evaluatedCount + bestScoreInIteration
  │
  ▼
Stop-condition check (noImprovementCap, maxCandidates, timeLimit, maxIterations)
  │
  ▼
runner.maybeCompleteIteration(loopId, iterationIndex)
  │  • Reads evaluatedCount vs actualCandidateCount (re-read from DB)
  │  • If complete: mark iteration DONE, copy top-1 to loop's best, schedule next iteration
  │
  ▼
runner.runIteration(loopId, iterationIndex+1, parent=loop-local-best, ...)
  │  • Builds HybridLoopConfig
  │  • Creates new SearchRun
  │  • Calls HybridLoopGenerator.generate
  │  • Publishes StrategyGenerated per candidate (with correct candidateId)
  │  • Auto-enqueue handles backtest → evaluation → StrategyEvaluated
```

Two writers, one owner per field:
- `LoopOrchestratorService` owns `totalEvaluated`, `noImprovementCount`, `bestScoreSoFar` on LoopRunState.
- `LoopOrchestratorRunner` owns `bestStrategyVersionId`, `bestStrategySymbolId`, `bestStrategyTimeframe`, `bestTotalReturn`, `bestWinRate` on LoopRunState and the iteration table.
- Both writers cooperate on iteration completion (runner waits for orchestrator to update counters).

## 17. Remaining Known Issues

1. The PowerShell e2e script's `[16]/[19]` timeout can cause an HTTP retry, producing a duplicate backtest for the same candidate. The orchestrator's dedupe catches this, but on rare occasions (rapid concurrent events) 1 duplicate can slip through (TOCTOU race on in-memory Set). Acceptable per the user's spec.
2. `HybridLoopGenerator` mutation occasionally produces an RSI composite with `buyThreshold >= sellThreshold`, causing the backtest to fail validation. This is a generator bug, not a lifecycle bug; the loop correctly handles it via `BacktestFailed`.
